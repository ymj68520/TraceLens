# 有预算的候选选择与文件研判

本模块改造既有文件选择阶段，继续使用任务索引、来源读取、文件研判、图谱与报告流程。当前策略为 `candidate-selection:v3`。FULL、SMART、Python 单镜像/多镜像筛选及批量文件分析入口共享原生计划；旧的模型按文件名筛选选项也进入同一计划。模型继续负责被准入材料的内容研判。

## 选择步骤

1. 扫描任务 `files.db` 内全部普通文件，保留 task/source/partition/inode/path/deleted 身份。候选范围仍服从原有场景筛选。
2. 按材料作用维护有界类别候选池，并保留独立探索池。稳定来源键打破同分，不依赖 SQLite 返回顺序。路径角色仅影响读取顺序，不是违法或相关性结论。
3. 经 `FileExtractor::readSourceRange` 在已登记来源中读取最多 64 KiB，识别真实格式、可读文本及完整小文件哈希。不会把逻辑路径或 `source:v1` 引用当作宿主路径打开。
4. 在独立额度内运行本地语义探测。SQLite 每表抽样 5 条，EVTX 最多扫描 128 条，使用与正式分析一致的结构化解析器。签名识别、部分可读、仅元数据、解析失败、未探测分别记录。
5. 按完整内容包 SHA-256 形成保守的代表组，结合类别份额、多样性软降权和探索名额选择。原始来源和组成员始终保留。SQLite 主文件单独的哈希不能代表带 WAL 的完整内容包；同名同大小不构成重复；空白相似模板只参与调度，不硬删除。
6. 冻结带摘要的选择计划，随后每次模型请求及重试先原子预留预算。成功写入文件分析结果后记录来源完成状态；失败或预算不足保留未完成状态。

自动选择初始份额为：文档/业务配置 20%、操作/系统活动 30%、程序/持久化配置 20%、浏览/通信数据库 15%、媒体 5%、探索 10%。不足份额回流到其他合格来源，因此最终比例可以不同。缓存最多占配置数量的约 5%。这些是初值，不能视为经过全盘召回率验证的最优比例。

`file_references` 显式来源走 explicit 通道，绕过类别软配额、缓存配额和内容代表合并，但仍受数量、读取能力、有效内容和模型硬预算约束。未准入项目返回中文暂缓原因。

## 配置

| 配置 | 默认/含义 |
| --- | --- |
| `LLM_MAX_FILES` | 文件研判上限，沿用原配置默认 500 |
| `FILTER_MAX_FILES` | 默认 0；正值进一步收紧，不能扩大原生上限 |
| 请求 `max_files` | 正值进一步收紧上述限制；0 表示采用配置，不代表无限 |
| `LLM_SMART_CANDIDATE_FILES` | 候选池上限，沿用原默认 1000 |
| `SELECTION_MAX_PROBE_FILES` | 默认 `min(2000, 候选上限)` |
| `SELECTION_MAX_PROBE_BYTES` | 默认 128 MiB，范围读取预留额度 |
| `SELECTION_PROBE_BYTES_PER_FILE` | 默认及最大值 64 KiB |
| `SELECTION_MAX_SEMANTIC_FILES` | 默认 500 |
| `SELECTION_MAX_SEMANTIC_BYTES` | 默认 1 GiB，语义探测来源组件包额度 |
| `SELECTION_MAX_SECONDS` | 默认 300 秒，探测时间窗口 |
| `SELECTION_SEED` | 默认 `tracelens-selection-v1`，稳定探索种子 |
| `LLM_ANALYSIS_MAX_CALLS` | 默认文件上限的 2 倍，每次派发与重试均占用 |
| `LLM_ANALYSIS_MAX_TOTAL_TOKENS` | 默认调用上限 × 文本模型上下文；保存的是预留上界 |
| `LLM_CONTEXT_LENGTH` | 最终请求上下文上限，已传入实际 C++ 模型配置 |
| `LLM_VISION_IMAGE_TOKEN_BOUND` | 默认 0；配置可靠的每图像上界后才允许计划内视觉模型请求 |

原有 `LLM_MAX_FILES=0` / 候选配置为 0 的兼容行为被限制为最多 100000，而非无穷大；仍受其余预算约束。单来源主文件完整读取最多 256 MiB，默认组件包最多 320 MiB。更大的文件暂缓，不能自动宣称已完成研判。

文本预算在系统提示、调查要求、正文及中文输出约束全部拼接后校验。对当前 byte-BPE 适配模型使用序列化 UTF-8 字节作为保守 token 上界，另留消息封装余量，不使用“字符数除以四”。这可能少用上下文空间。接入不同分词机制的模型时应补充可验证的计数器或可靠上界。正文不会再同时完整出现在 content 和 instruction。实际用量未知或失败不退还预留，避免重试超额；审计中的预留数不等于供应商实际计费数。

## 来源与状态边界

- E01/TSK 走真正范围读取；鸿蒙用已索引容器偏移；小米用已验证 inode/runs。
- 当前 XFS helper 不提供真正有界的范围读取，该探测返回未支持/未探测，不静默退回整文件读。能否通过其他已支持的有界语义探测准入，按具体来源与额度决定。
- 首部签名只能确认格式，不能保证正式解析成功。正式研判仍须经原有读取和解析门控。
- EVTX 空日志快速判断要求文件头、块头 CRC、活动块数量、已知空块标志、记录偏移与大小条件一致。它仅描述标准可见记录，未扫描恢复记录、inactive chunks 或未分配空间。
- `partial` 中有效记录可以进入研判；错误和诊断不会作为证据正文。未探测、未入选或暂缓均不表示无关、无内容或不存在行为。
- 未配置视觉上界时，自动选择中的图像暂缓；不把受限项目标记为已完成全功能视觉分析。

## 计划、续跑和审计

计划键包含策略版本、预算、模型配置摘要、案情摘要（通过 HTTP 提交时）、来源版本和实际索引字段摘要。模型缓存写回不会改变索引摘要。规则变更应升级版本，不覆盖旧计划。

每份计划带 `plan_digest`，C++ 与 Python 校验相同的规范 JSON SHA-256。Python 的 `selection_run` 保持各流程使用准确的计划，避免并发时误取最新计划。多镜像使用同一预算所属数据库；预算不会按镜像数扩大。

任务数据库保存：

- `selection_runs`：冻结计划与候选理由。
- `selection_probe_budget` / `selection_probe_cache`：探测预留和结果。
- `selection_budget` / `selection_call_ledger`：调用数、令牌上界与每次预留。
- `selection_execution`：每个来源在特定计划内的完成/失败状态。

预算更新使用 SQLite `BEGIN IMMEDIATE`。同计划续跑复用已完成来源，预算不重置；上下文/策略变更产生新计划。整个任务的记录解析、聚合研判和报告阶段仍沿用各自原流程，此处额度覆盖文件研判阶段，不代表全案所有模型费用。

`POST /api/forensics/files/selection-plan` 创建或复用计划；`GET` 只读查看，不触发探测。原文件页嵌入中文“候选选择审计”，展示候选/探测数、类别分布、未完成情况、预算以及最多 50 条来源理由。完整计划保存在数据库。

## 验证方式

- 原生测试：行序稳定、缓存洪泛、多个用户文档、空/失败门控、完整内容分组、SQLite WAL 边界、EVTX 空块完整性、显式来源范围、并发预算与续跑。
- Python 测试：最终消息预算、UTF-8 安全裁剪、重复正文、零温度、计划摘要与确切绑定、跨任务拒绝、视觉预算、音视频路由和调用并发。
- `tests/integration/candidate_selection_probe.cpp` 在隔离数据库中执行正式选择服务，可对真实检材重放；`--evtx-headers` 用于与独立解析器交叉核对。
- 2026-10-25 PC.E01 重放采用 5000 候选、1000 分析代表、2000 范围探测和 500 语义探测上限。浏览器历史、用户公告及配置五个核对点全部入选。重复计划一致，模型调用为 0。这证明已知遗漏与预算行为修复，不证明全盘召回率或最终案情报告质量。

## 服务器材料修正（2026-10-27）

`candidate-selection:v6-server-resources` 提高站点配置、账户认证记录、命令历史和第一方控制器/模型/服务代码的优先级。软件依赖、前端插件目录、内核源码、软件安装包头和手册按包抽样，整体最多 20 份、同包最多 2 份；不会删除来源，也不把不同模板或语言资源视为同一证据。第一方 `public/js` 及安装过程日志仍保留原优先级，显式来源请求仍可读取这些抽样目录中的其他文件。

本次真实镜像进一步发现：只统计 vendor 等已识别目录，会漏算 `public/static/plugs` 中的前端插件，不能用该统计直接宣称低噪声。验收需同时按实际路径复查资源分布，并核对站点配置、控制器和认证记录是否入选。关键来源的命中率不等于全盘重要文件召回率。
