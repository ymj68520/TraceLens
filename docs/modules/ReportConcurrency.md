# 报告有界并发与全文收束

本功能用于原材料自主研判、案情对照报告与自动报告尾段，不增加取证工作流。新输入采用 envelope v9、阶段提示契约 v4、发布 manifest 1.4。历史 v1–v8 输入继续使用冻结的原执行路径；旧正文、提纲、来源哈希和输入哈希不改写。

## 调度与预算

新配置 `REPORT_EXTRACTION_CONCURRENCY=4`、`REPORT_WRITING_CONCURRENCY=2`、`REPORT_REVIEW_CONCURRENCY=2` 在准入时写入 `execution_policy`。允许设为 1 做串行对照，范围分别为 1–4、1–2、1–2。运行中修改配置不改变已经冻结的任务。

事实提取与主体写作、逐章复核使用有界工作池。只创建固定数量 worker，结果按来源/章节原顺序归并，不按响应先后改变正文顺序或覆盖范围。任一必需写作任务失败时取消并等待同组任务退出，已完成的审计记录保留，不发布半份报告。新版本报告之间还共享同一 Python 进程/事件循环中的四个文本请求槽位；图像投影保留原单路及图像预算。这不是跨进程、跨 C++ 文件分析和 Graphiti 的统一限流器，多服务部署仍须遵守模型端总额度。

事实提取先按固定顺序覆盖首轮来源，再为失败或部分无效来源分配一次定向重试。读取范围、拒绝原因、重试来源及暂缓项全部保存；某窗口后续成功不会抹去同材料另一窗口的失败。发现数量按固定归并顺序截定，未纳入项保留限制。

沿用原 `ReportBudget`。提取调用上限为总调用预算减去尾段预留：预留 `min(36, max(10, max_calls // 2))` 次。阶段上限和总调用/令牌/时间额度在 SQLite 同一个 `BEGIN IMMEDIATE` 事务中核验；并发、重试和多个 worker 不重置额度。请求完整组装后做上下文检查，超限明确失败。SQLite 审计写入移到线程执行，避免阻塞异步模型请求；外部请求期间不持有数据库写事务。

## 主体先完成，概述与结论后生成

统一提纲确定全部允许发现与引用，主体章节最多两路撰写、最多两路逐章复核。随后以已经通过校验的主体全文为上下文，依次生成概述和结论。已生成正文仅用于保持解释一致，事实依据仍来自冻结材料及引用，不能成为新增原始证据。

概述和结论可以引用主体已交代的所有发现，另列必须覆盖的关键发现；不强迫摘要逐项复述整份主体，也不允许使用主体范围外的新发现。每个段落仍须绑定至少一个允许发现及对应引用，衔接和建议段也不能空绑来源。主体章节仍必须交代其全部规划发现。

短引文是定位锚点，并不包含结构化记录的所有字段。写作、逐章和全文复核同时读取相关的冻结记录及其类型、限制、哈希和字符范围，避免因短片段缺少字段而错误否定原记录中的运行次数、文件名或配置状态。机器视觉观察保留 `machine_visual` 标记，不能冒充原始文字。原记录仍受引用白名单和完整请求上下文预算约束；主体共同出现仍不能自动证明行为关系。全文复核同时接收逐段发现/引用映射，避免把不同记录的字段误接。

主体压缩、语义修复或全文复核改变正文后，概述和结论重新收束。发布产物保存两章实际读取的主体 SHA-256，读取和发布时再从最终正文计算核对；不能让旧结论绑定到改写后的主体。可选的关键发现字段在旧提纲序列化时省略，保留原提纲摘要。

全文辅助复核同时读取发现与原文支持/反向片段，区分事实冲突、无依据的肯定事实、范围越界与重复/衔接建议。前三类阻止发布，后两类保留为中文编辑建议，不把谨慎限制或正常摘要复述当作事实冲突。意见须指向实际段落；段落编号错误但引文在指定章唯一出现时由服务器纠正并留痕。一条无效意见不能抹掉其他有效的阻断意见。

最多修复四个受影响章节，复核仍有明确问题或已知问题未完成复核时阻止发布。初次辅助复核因预算或协议原因没有完成，可保留明确质量限制的初步报告，不能标为已完成语义核验。所有正文继续遵守 4–6 章、20,000 字符硬上限和单章 35% 上限。

## 可观测性与验收方法

原报告审计面板展示冻结的 4/2/2 参数和全文辅助复核结果。审计记录保存实际峰值并发、分阶段时间、每次模型请求时长、提取安排、收束输入及其摘要。通过原来源校验、中文约束和发布门控后才交付报告。

本轮对照使用相同的 173 份冻结 PC 材料及相同来源集合哈希。串行组 1/1/1 与并发组 4/2/2 均启用上述收束逻辑，每组最多 72 次调用、相同上下文/输出/令牌/时间上限和模型参数，连续执行，不用缓存响应加速计时。实际调用次数可能因校验重试不同而不同，必须和耗时一起报告。

真实对照暴露了中文限制措辞、复核上下文不完整和嵌套修复键冲突，修复验证另行使用精确请求响应回放，新增模型调用单独记账。回放耗时不用于冷启动性能结论。已完成阶段的时间、完整报告是否发布及诊断累计成本必须分开呈现，不能把中途失败的运行时间当成完整报告生成时间。

覆盖率按冻结文本投影统计，不能当成原文件全文或整盘覆盖率。远端模型在相同温度下仍可能产生不同输出；单次对照的覆盖/连贯性差异不能全部归因于并发，也不构成统计显著性证明。失败轮次单独保存，未形成合格报告的耗时不作为完整生成提速结论。

## 服务器镜像验收修正（2026-10-27）

新准入使用 `final-report:evidence-only:v6` / `final-report:case-guided:v6`，输入仍为 schema 9、报告仍为 1.4；旧提示版本保留原协议。v6 用明确的“撤销异议 / 保留异议 / 需要复核”动作取代容易产生否定歧义的复核判定。撤销异议仍需该段实际引用的冻结原文，重复引句必须校验字符位置；协议或引文错误最多再纠正一次，不从模型理由文本猜测放行结论。

v6 全文最多两轮有限修复，每轮最多四章；改动主体后必须重新生成概述与结论并校验主体哈希。问题持续存在时仍阻止发布。HTTP 429 触发本进程报告请求的共享等待，遵守 Retry-After，缺省等待 30、60 秒，每次请求最多三次派发。失败和重试均占原调用/令牌/时间预算，认证失败不重试。

原任务恢复入口在记录的 `FINALIZING.report` 边界核对原镜像绑定、文件与事件内容摘要；与已完成摄取一致时仅续跑报告。SQLite 检查点及摄取水位变化不代表新材料，记录或检材变化则不能使用该快速路径。既有部分分析及图谱失败范围保留，不借报告完成改写成全量成功。
