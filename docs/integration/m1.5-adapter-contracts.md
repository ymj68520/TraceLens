M1.5 is documentation and read-only contract work. It does not modify production, frontend, schema, or tests and does not execute the final merge. The purpose is to make M2 implementable without making architecture decisions inside a 159-file conflict.

M1 established these owners:

- Local `InvestigationRepository` and split services are the sole canonical Investigation writer.
- Local R2 Report Evidence, frozen generation, citation validation, immutable report/version and manifest are the sole factual/publication authority.
- Remote Workbench and Final Report code is retained only through adapters or rebuildable derived projections.
- Remote Chain B writer, client-authoritative database paths, and raw exception exposure are regressions and require caller migration.

## B. Namespace Freeze

The existing local namespace remains unchanged:

```text
/api/investigation/...
/api/reports/evidence
/api/reports/generate
/api/reports/generations/{generation_id}
```

Remote Workbench facade namespace is frozen as:

```text
/api/investigation/workbench/{task_id}/...
```

The facade must be registered before any broad dynamic route only within its own explicit prefix. It must not add `/{task_id}` under the existing canonical `/api/investigation` router. Therefore:

- `/api/investigation/graph` remains the local graph route.
- `/api/investigation/analyses` remains the local Secondary Analysis route.
- `/api/investigation/events/{event_id}/refresh` remains the local Event Refresh route.
- `/api/investigation/workbench/{task_id}/...` is the only remote-shaped facade namespace.
- No route may use `latest`, implicit current analysis, or an unscoped report path.

Remote frontend service functions must be renamed or configured to target the facade namespace. The existing local service exports remain available for Phase F and local workflow compatibility.

### Workbench ViewModel

`GET /api/investigation/workbench/{task_id}/overview` may return one aggregate read model:

```json
{
  "task": {"task_id": "...", "status": "completed"},
  "evidence": [],
  "snapshots": [],
  "analyses": [],
  "effective_analysis": null,
  "events": [],
  "report_evidence": [],
  "graph": {"nodes": [], "edges": []}
}
```

Every field is read from local services:

- task: trusted C++ task lookup;
- evidence/detail: local Evidence resolver and read-only source DB;
- snapshots/analyses/claims: local InvestigationReadService;
- effective analysis: local accepted-first selector;
- events/evidence links/refreshes: local Event service and EventRefresh reader;
- report evidence: local ReportEvidenceService;
- graph: local GraphReader.

The aggregate endpoint is read-only. Bootstrap must not silently create snapshots or events. Any explicit capture or mutation uses the canonical local endpoint and exact ID returned by it.

## F. Final Report Render Input Contract

Remote Final Report code cannot read current Files, current Analysis, or current Graph as factual authority. It receives one exact immutable input from the local R2 reader:

```json
{
  "task_id": "task-uuid",
  "report_id": "report-uuid",
  "report_version": 7,
  "manifest_hash": "sha256:...",
  "manifest": {
    "citations": [],
    "claims": [],
    "evidence": []
  },
  "narrative": {
    "title": "...",
    "sections": []
  },
  "citations": [],
  "metadata": {
    "report_kind": "llm_generation",
    "input_hash": "sha256:...",
    "prompt_version": "..."
  }
}
```

Contract rules:

- `task_id`, `report_id`, `report_version` are mandatory and jointly identify one local immutable version.
- `manifest_hash` must be computed from the exact local manifest; the renderer must reject mismatch.
- `narrative`, `citations`, claims and evidence are copied from the local exact report/version reader, not rebuilt from live databases.
- There is no `latest=true`, implicit version, current-analysis lookup, or dynamic Report Evidence rebuild.
- Rendering is read-only relative to canonical R2 state.
- Rendering failure leaves the local report `completed`, readable and citation-traceable.

## G. Derived Store Ownership

M2 may use a task-scoped derived store only with this exact identity:

```text
source_identity = (task_id, report_id, report_version, manifest_hash)
render_candidate_key = (task_id, report_id, report_version, section_id, render_version)
validation_key = (task_id, report_id, report_version, candidate_id, validation_version)
```

Rules:

- The store is located under the task-owned investigation/report output root selected by the local trusted task path, never a client-supplied path.
- A single derived SQLite file may contain render candidates and validation rows only if its ownership is explicit and it is opened existing-only for read paths.
- It must not be named or treated as the canonical `reports.db`.
- It must not use `latest`, title, task-only, or mutable current-state identity.
- It must be rebuildable from the local immutable report/version/manifest and exact render input.
- Task deletion removes or tombstones derived data only after canonical task deletion rules; no derived write may resurrect a task.
- If a canonical report/version is unavailable or hash-mismatched, rendering fails closed.
- If rendering fails, the local R2 report remains completed and readable.
- `final_report_publications` is not merged. Remote “publish” is removed from the adapter or redefined as a non-authoritative export/delivery receipt in a later explicit decision. It cannot set a second factual `published` state.

## H. Citation Validation Ownership

Local R2 owns factual citation validity:

- Evidence exists under the exact task and key.
- Report Evidence binding is explicit.
- Analysis binding is exact and accepted, or original-only NULL.
- Claim ID and Evidence key traceback are exact.
- The frozen generation input and manifest are authoritative.

Remote citation validation may check only presentation concerns:

- broken section anchor;
- missing render target;
- duplicate display citation;
- missing presentation metadata;
- HTML/Markdown formatting integrity.

Remote validation cannot change Evidence truth, claim grounding, citation eligibility, report completion, or publication status.

## N. Timeline, Android, Media and ServiceManager Rules

- do not initialize a second Remote Investigation writer lifecycle;
- derived render repositories may be task-scoped caches and must close/clear with task lifecycle.

### Merge technique and commit boundaries

- Use ordinary `git merge --no-ff origin/Dev`; do not rebase, reset, cherry-pick rewritten remote history, or use whole-file ours/theirs as a default.
- Resolve one family at a time and inspect `git diff --cached` after each family.
- A merge cannot receive normal intermediate commits before all conflicts are resolved. Therefore use temporary checkpoints outside Git (diff exports or branch refs only if explicitly needed), then create the merge commit after minimum gates.
- Follow-up adapter/frontend/test fixes are independent commits after the merge commit.
- If a family requires a new canonical schema, a second writer, or changed Evidence/R2 semantics, stop and return `NO-GO` rather than forcing the merge.
