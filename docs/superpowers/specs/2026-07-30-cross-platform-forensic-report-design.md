# 跨平台结构化取证报告设计

**日期：** 2026-07-30  
**状态：** 已确认  
**范围：** TraceLens 前端在线报告、版本化报告快照、离线 HTML 报告包；支持 Android、Windows、Linux，兼容单任务与多镜像案件

## 1. 背景

参考项目 `~/projects/Forensics/Android_report` 提供的不是单纯的分析结论，而是一套可浏览的结构化取证数据报告：左侧多级证据目录、全文搜索、案件与检材信息、分类统计、逐条痕迹表格、聊天式记录、附件预览和分页跳转。

TraceLens 当前已有的报告能力主要位于 `web/src/pages/CaseIntelligence.jsx` 和 Python `case_analysis` 服务中。后端生成“案件概述、时间线梳理、证据分析、关键发现、结论与建议”五章 Markdown 智能研判，前端在案情研判页面直接渲染该文本。此能力不能替代完整的结构化痕迹报告，也尚未形成统一的 Android、Windows、Linux 报告浏览和离线交付机制。

本设计把两类能力合并为一份报告：

1. 类似参考报告的结构化取证痕迹浏览；
2. TraceLens 现有五章智能研判。

## 2. 已确认的产品决策

- 报告同时包含结构化痕迹和五章智能研判。
- 同时支持单任务报告和多镜像案件报告。
- 第一阶段交付在线浏览和离线 HTML 报告包，不提供 PDF/DOCX。
- 结构化报告包含全部已解析痕迹，并突出已删除、异常、高相关和纳入研判的记录。
- 报告采用不可变的版本化快照；数据变化后生成新版本，历史版本保持不变。
- 敏感字段展示原文，不自动脱敏。
- 离线包包含缩略图和允许的小型预览；大型或敏感原始附件只记录证据路径与哈希，不默认复制。
- 平台章节依据快照中实际存在的数据自动编排；一个任务可以同时包含多个平台。
- 不逐像素复刻参考报告的 frameset/Bootstrap 实现，而是保留其目录、搜索、统计、明细和分页能力，使用现代 React 页面实现。

## 3. 目标与非目标

### 3.1 目标

1. 建立统一、可扩展的跨平台报告协议。
2. 在线报告和离线 HTML 使用同一份快照、同一套渲染组件和相同的信息结构。
3. 支持大规模痕迹数据的按需加载、分页和搜索，不要求浏览器一次加载全部记录。
4. 支持单任务和案件两个层级，案件报告按检材分组并提供跨检材综合内容。
5. 保留现有五章研判、文件引用和事件引用能力。
6. 为每个报告版本记录来源、生成器版本和完整性信息，满足复核与审计要求。
7. 平台适配器失败时尽可能产出带警告的可用报告，不丢失其他平台内容。

### 3.2 非目标

- PDF 或 DOCX 导出。
- 在线编辑报告并覆盖原版本。
- 自动脱敏。
- 默认打包全部原始附件。
- 复刻参考报告的旧 frameset、固定页数或旧 Bootstrap 外观。
- 在本需求中新增尚不存在的取证解析器。
- 立即删除现有 `case-report` 和 `case-report-by-case` API。

## 4. 候选方案与结论

### 4.1 方案 A：统一报告快照模型

后端生成版本化报告快照，把案件信息、检材信息、平台分类、痕迹统计、分页索引、重点标记、附件预览和五章研判统一固化。在线页面和离线 HTML 都读取同一快照。

优点是在线/离线一致、适合审计、支持大数据量、平台扩展边界清晰，也是本设计采用的方案。

### 4.2 方案 B：前端实时聚合现有 API

前端分别请求各类 API 并即时拼装报告。后端改动较少，但无法可靠满足不可变版本、在线/离线一致、多镜像聚合和大数据量导出需求，因此不采用。

### 4.3 方案 C：三个平台分别实现报告

Android、Windows、Linux 各自维护页面、数据结构和导出器。平台定制能力高，但会重复实现版本、搜索、分页、案件信息和导出，并使混合平台报告割裂，因此不采用。

## 5. 产品结构与页面布局

### 5.1 路由与入口

新增独立的“取证报告”工作区：

- 单任务：`/reports/task/:taskId`
- 多镜像案件：`/reports/case/:caseId`

任务列表中的 `Report` 操作切换到新路由。案件页提供案件报告入口。旧 `/case-report?task_id=...` 和 `/case-report?case_id=...` 路径兼容重定向到新路由，避免旧链接失效。

每个入口先展示目标的报告版本。默认打开最新的 `ready` 版本，同时可查看历史版本或生成新版本。旧版本只读，不允许覆盖修改。

### 5.2 页面布局

#### 顶部报告栏

包含：

- 报告标题、任务或案件名称；
- 报告版本、生成时间和状态；
- Android、Windows、Linux 平台徽标；
- 生成新版本；
- 导出离线 HTML；
- 版本历史。

#### 左侧目录与全文搜索

包含：

- 全文搜索框；
- 上一条/下一条匹配；
- 多级报告目录；
- 每个目录节点的总数、已删除数、高风险数和重点证据数；
- 按快照实际数据生成的平台及分类；
- 点击章节节点滚动到正文；
- 点击叶节点加载对应分类和分页数据。

#### 中央正文

依次展示：

1. 报告封面；
2. 案件与生成信息；
3. 检材/镜像清单；
4. 按检材分组的结构化痕迹；
5. 跨平台综合时间线；
6. 重点证据与异常；
7. 五章智能研判；
8. 数据完整性、来源和生成说明。

#### 分类分页

静态参考报告把整个报告切成固定 HTML 页。本设计改为“章节导航 + 分类记录分页”：

- 每个痕迹分类独立分页；
- 支持页码跳转、前后页和每页数量；
- 章节正文不受固定总页数限制；
- 大分类只加载当前页。

### 5.3 响应式行为

- 宽屏：目录固定，正文独立滚动。
- 窄屏：目录变为抽屉，搜索入口保留在顶部。
- 宽表格横向滚动。
- 聊天、图片、时间线使用专用组件。
- 离线 HTML 保留同样的目录、搜索、分页和预览体验。

## 6. 系统架构

### 6.1 统一生成服务

新增 `ForensicReportService`，负责报告生命周期和跨平台编排。React 前端不直接理解平台数据库表结构。

生成流程：

1. 接收目标范围：单任务或案件。
2. 冻结本版本涉及的任务、检材和数据源清单。
3. 探测每个检材实际存在的数据源和平台。
4. 调用平台及通用适配器，把数据规范化为统一报告协议。
5. 生成目录、统计、分页数据分片和搜索索引。
6. 获取当前五章智能研判；若本次要求重新研判，则等待研判完成后再封版。
7. 生成附件预览清单、源证据引用和哈希。
8. 写入不可变报告版本。
9. 在 manifest 和必要索引校验完成后将版本标记为 `ready`。
10. 按同一快照构建离线 HTML 包。

### 6.2 适配器边界

首期适配器：

- `AndroidReportAdapter`
- `WindowsReportAdapter`
- `LinuxReportAdapter`
- `CommonFilesReportAdapter`
- `TimelineReportAdapter`
- `AnalysisChaptersAdapter`

每个适配器负责：

- 探测自己的数据是否存在；
- 读取平台数据库或现有服务结果；
- 输出统一目录、统计和记录；
- 报告缺表、缺列、数据损坏和部分失败；
- 不负责页面渲染、版本管理或导出。

适配器互相独立。单个平台失败时，编排层可以继续处理其他平台并产出带警告的报告。

### 6.3 在线与离线数据访问

报告渲染层只依赖统一的数据访问接口：

- 在线实现从 HTTP API 读取 manifest、分页分片、搜索结果和预览资源；
- 离线实现从相对路径 JSON 和本地预览目录读取相同协议。

因此在线报告和离线报告共用 React 渲染组件，不维护两套页面。

## 7. 版本化快照模型

### 7.1 报告版本

每个版本至少包含：

- `report_id`
- `version`
- `scope_type`: `task | case`
- `scope_id`
- `status`: `queued | generating | ready | failed`
- `title`
- `case_description`
- `platforms`
- `task_ids`
- `generated_at`
- `generated_by`
- `generator_version`
- `schema_version`
- `source_fingerprints`
- `manifest_path`
- `offline_bundle_path`
- `warnings`
- `error`

同一 `scope_type + scope_id` 下版本单调递增。已发布版本不可变；重新生成创建新版本。

### 7.2 来源冻结与指纹

生成开始时冻结：

- 任务与检材 ID；
- 数据库路径和可用状态；
- 数据库文件大小、修改时间和可获得的哈希；
- 相关分析结果的更新时间或版本；
- 附件预览候选清单。

生成过程中源数据库可能继续变化。适配器应使用只读连接和一致性读取策略；`source_fingerprints` 记录生成所依据的来源状态。报告版本完成后不再追踪实时变化。

### 7.3 Manifest

主 manifest 只保存导航和摘要：

- 报告元数据；
- 案件信息；
- 检材清单；
- 目录树；
- 平台与分类统计；
- 章节摘要；
- 五章研判；
- 数据分片索引；
- 搜索索引元数据；
- 附件预览索引；
- 警告；
- 完整性信息。

不得把全部痕迹记录塞进单一 manifest。

### 7.4 数据分片

大量数据按“检材 → 平台 → 分类 → 页”分片。例如：

- Android / 通讯录 / 第 1 页；
- Android / 微信聊天 / 第 12 页；
- Windows / 事件日志 / 第 3 页；
- Linux / SSH 登录 / 第 2 页。

每个分片包含总数、页码、页大小、记录和分片哈希。在线和离线使用相同格式。

### 7.5 统一记录协议

平台适配器输出统一外壳：

- `record_id`
- `category`
- `title`
- `timestamp`
- `source_path`
- `source_table`
- `source_record_id`
- `data_state`: `existing | deleted | recovered | unknown`
- `severity`
- `is_relevant`
- `hashes`
- `fields`
- `attachments`
- `analysis_references`

`fields` 保留分类自身字段。前端通过分类渲染注册表选择专用组件；未注册分类使用通用键值或表格组件。

`record_id` 必须稳定且不依赖本次分页顺序，建议由作用域、检材、平台、分类、来源表和来源记录键构造或哈希得到。

## 8. 单任务与案件报告

### 8.1 单任务

- 包含一个检材组；
- 同一检材可以出现多个平台；
- 五章研判来自该任务的现有 `case_analysis` 报告；
- 时间线和重点证据限于该任务。

### 8.2 多镜像案件

- 包含多个检材组；
- 每个检材独立展示平台和分类；
- 目录可以按“检材 → 平台 → 分类”展开；
- 提供跨检材综合时间线；
- 提供案件级重点证据；
- 五章研判使用案件级 `case-report-by-case` 结果；
- 搜索覆盖该版本纳入的所有检材。

## 9. 跨平台内容映射

平台内只显示实际存在的数据分类。任务创建时勾选的场景可作为探测提示，但不强制生成空章节。

### 9.1 通用章节

- 报告说明和生成器版本；
- 案件信息；
- 检材/镜像信息；
- 分区和文件系统信息；
- 镜像或源文件哈希；
- 文件证据；
- 已删除/恢复文件；
- 综合时间线；
- 重点证据和异常；
- 五章智能研判；
- 完整性与生成说明。

### 9.2 Android

- 设备与系统信息；
- SIM 和账号信息；
- 通讯录；
- 短信与彩信；
- 通话记录；
- 应用列表与使用情况；
- 应用数据库；
- 即时通信，按应用、账号和会话分层；
- 位置与出行；
- 浏览器与搜索记录；
- 媒体及附件；
- 删除/恢复数据；
- 安全相关信息与密码提示。

聊天记录采用会话式组件，列表数据采用表格或详情组件，媒体展示缩略图。

### 9.3 Windows

- 系统、主机和版本信息；
- 用户与组；
- 注册表；
- Windows 事件日志；
- 登录与账户活动；
- Prefetch；
- Amcache / Shimcache；
- LNK / Jump Lists / RecentDocs；
- 浏览器历史、下载、书签、Cookie 和登录信息；
- USB 与外接设备；
- 服务、计划任务和自启动项；
- 网络配置与连接痕迹；
- 回收站和删除文件；
- 可执行文件、DLL 与异常分析；
- 内存痕迹，仅在存在内存分析结果时显示。

### 9.4 Linux

- 系统、发行版、内核和主机信息；
- 用户、组与权限；
- 登录记录；
- Shell 历史；
- SSH 密钥、配置和会话痕迹；
- systemd、auth、syslog 和 audit 日志；
- 进程、服务、定时任务和启动项；
- 软件包与安装记录；
- 网络配置、连接和防火墙；
- Docker 和容器痕迹，仅在实际存在时显示；
- Web 服务和服务器日志，仅在实际存在时显示；
- SUID、Capabilities、SELinux 等安全异常；
- 删除/恢复文件。

### 9.5 统一重点标记

所有分类统一展示：

- 数据状态；
- 风险等级；
- 是否纳入案情证据；
- 来源路径、来源表和记录 ID；
- 原始文件或附件哈希；
- 被五章研判引用时的反向链接。

敏感字段按已确认需求展示原文。报告访问权限沿用 TraceLens 的认证与授权边界。

## 10. 五章智能研判集成

保留现有章节：

1. 案件概述；
2. 时间线梳理；
3. 证据分析；
4. 关键发现；
5. 结论与建议。

现有 `[[file:完整路径]]` 和 `[[event:事件类型@时间窗口/目录]]` 格式继续使用。快照生成时解析这些引用并保存结构化反向关系：

- 点击文件引用跳到对应检材、平台、分类和记录；
- 点击事件引用跳到综合时间线或事件簇；
- 结构化记录显示“被哪些章节引用”；
- 引用目标未纳入快照时显示明确的“当前版本未找到目标”提示，不进行模糊猜测。

当前五章文本可以直接进入快照。如果用户在生成报告时选择重新研判，报告任务必须等待研判完成并读取新结果后才能封版。

## 11. 在线 API 设计

具体 URL 可在实施计划中依据现有 FastAPI 路由风格确定，但资源能力必须覆盖：

1. 为任务或案件创建报告版本；
2. 查询生成任务和阶段进度；
3. 列出目标的版本历史；
4. 获取指定版本 manifest；
5. 获取目录分类的数据页；
6. 搜索指定报告版本；
7. 获取允许展示的预览附件；
8. 请求构建离线包；
9. 下载已完成的离线包；
10. 获取版本警告和失败摘要。

生成采用后台任务。前端刷新后可以根据 `report_id` 恢复状态。只有 manifest、必要索引和完整性记录全部落盘且校验通过后，版本才能进入 `ready`。

## 12. 搜索设计

### 12.1 索引范围

搜索覆盖：

- 目录和章节标题；
- 统一记录的 `title`；
- `fields` 中可搜索的主要文本字段；
- 路径、账号、号码和哈希；
- 五章研判文本。

搜索只覆盖快照内容，不读取该版本生成后新增的数据。

### 12.2 在线搜索

服务端查询该报告版本的独立索引，返回：

- 章节/记录定位；
- 匹配字段；
- 匹配摘要；
- 所属检材、平台和分类；
- 总命中数。

前端支持上一条、下一条、目录命中计数和正文高亮。

### 12.3 离线搜索

索引按检材、平台或分类拆分为轻量分片。离线页面按查询需要逐步加载，不在启动时载入全部索引。中文、路径、电话号码和哈希查询均需覆盖固定测试样例。

## 13. 附件与预览

### 13.1 默认策略

- 可安全内嵌的缩略图和小型文本预览复制到报告包；
- 音视频、文档和大型文件默认不复制原件；
- 原始证据路径和哈希始终保留；
- 在线报告只有在权限允许且源文件存在时才能打开原件；
- 离线报告只展示已打包的预览，不宣称原件可访问。

### 13.2 附件元数据

每个附件至少包含：

- 文件名；
- 原始证据路径；
- 大小；
- MIME；
- 哈希；
- 预览类型；
- 预览路径；
- 原件是否随包包含；
- 不可用原因。

### 13.3 安全要求

- 所有报告包内路径必须是受控相对路径；
- 禁止 `..` 路径穿越；
- 不根据证据文件名直接决定输出路径；
- 预览生成执行大小、类型和数量限制；
- HTML 和文本内容必须转义或经过受控 Markdown 渲染；
- 报告包不能包含指向本机绝对路径的可执行资源引用。

## 14. 离线 HTML 包

离线导出物为 ZIP，解压后可直接打开 `index.html`，不依赖 TraceLens 服务或网络。

建议结构：

```text
index.html
assets/
report/manifest.json
report/data/<evidence>/<platform>/<category>/<page>.json
report/search/<shard>.json
report/previews/<asset>
report/integrity.json
README.txt
```

在线和离线页面共用渲染逻辑。离线构建过程固定前端静态资源版本，并把版本号写入 manifest。

## 15. 完整性与审计信息

- manifest、数据分片、搜索索引和预览文件都写入 `integrity.json` 的 SHA-256；
- 报告顶部显示快照 ID、版本、生成器版本和完整性状态；
- 离线页面启动时验证关键清单；
- 提供“验证报告完整性”操作进行全包校验；
- 原始证据哈希与报告包文件哈希分开记录；
- 报告完整性通过只表示报告包未被修改，不等同于原始证据来源本身已完成司法级校验；
- 生成阶段、警告和失败摘要保留在报告元数据中。

## 16. 状态与错误处理

### 16.1 用户可见状态

- `未生成`：显示探测到的数据源与生成操作；
- `排队/生成中`：显示阶段、进度和当前平台，刷新后继续查询；
- `可用`：manifest 和必要资源完整；
- `带警告可用`：一个或多个非关键数据源失败或缺失，但报告主体完整；
- `失败`：关键清单、数据分片、索引或完整性生成失败；
- `版本模式不兼容`：提示使用新生成器创建新版本，不错误解析旧快照。

### 16.2 部分失败

以下情况可以产生带警告版本：

- 某个平台数据库不存在；
- 某个非关键分类表不存在或损坏；
- 原始附件已不可访问；
- 某个平台适配器失败，但其他平台和主 manifest 可完成；
- 个别预览生成失败。

以下情况必须整体失败：

- 无法写入或读取主 manifest；
- 目录或分片索引与实际数据不一致；
- 必要数据分片落盘失败；
- 完整性清单无法生成；
- 快照作用域无法确定。

失败版本保留错误阶段与摘要。重试创建新版本，不覆盖失败记录。

### 18.4 端到端验收数据

准备四套固定检材：

1. Android 样例；
2. Windows 样例；
3. Linux 样例；
4. Android + Windows + Linux 混合案件。

每套验证：在线报告、版本历史、全文搜索、重点标记、五章研判、离线 HTML、无网络打开、附件引用和完整性校验。

## 19. 验收标准

1. 已完成的 Android、Windows 或 Linux 任务可以生成结构化报告版本。
2. 报告目录只展示实际有数据的平台和分类。
3. 全部已解析痕迹可通过分类分页访问，重点、已删除和高风险记录有统一标记。
4. 单任务和案件报告使用同一页面与数据协议。
5. 案件报告按检材分组，并提供跨检材搜索、时间线和五章研判。
6. 五章中的文件和事件引用可以定位到结构化内容，或显示明确的未找到状态。
7. 同一报告版本重复打开内容不变；重新生成创建新版本。
8. 在线和离线 HTML 对同一版本展示相同章节、统计和记录。
9. 离线包解压后无需服务即可打开、搜索、分页和查看已打包预览。
10. 离线包不默认复制大型原始附件，但清晰显示原始路径、大小、类型和哈希。
11. 某个平台缺失或失败不会删除其他平台内容，并在报告中留下明确警告。
12. 报告包完整性校验可检测 manifest、数据分片或预览被修改。
13. 旧报告链接在迁移期仍可到达对应的新报告目标。

## 20. 实施边界建议

本需求虽然作为一个统一产品设计交付，但实施计划应按可验证的纵向切片拆分：

1. 报告版本与 manifest 基础设施；
2. 通用前端报告壳、在线数据适配器和版本页面；
3. Android 适配器与结构化渲染；
4. Windows 适配器；
5. Linux 适配器；
6. 案件级聚合、跨检材搜索和时间线；
7. 五章引用集成；
8. 离线 HTML 构建、附件预览和完整性校验；
9. 兼容迁移与端到端验收。

每个切片都必须使用真实或固定数据库 fixture 完成测试，避免三个平台全部实现后才发现统一协议无法覆盖实际数据。
