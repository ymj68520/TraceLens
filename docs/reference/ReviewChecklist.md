# 文档与代码评审清单

> 适用于文档 PR、代码 PR 中涉及文档同步的场景。目标不是检查格式，而是确认读者能从文档走到代码、从代码回到验证。每一项都可以标记通过/不适用/待修。

## 1. 事实准确性

- [ ] 文件路径在当前分支真实存在；
- [ ] 类名、函数名、枚举值与源码大小写一致；
- [ ] 端口来自代码或脚本，而不是旧 README；
- [ ] 参数名来自 handler/Pydantic 模型；
- [ ] 默认值来自实际读取点，并注明多处漂移；
- [ ] 表名/列名来自 CREATE TABLE；
- [ ] “支持”意味着有生产调用方，不是只有源码和单测；
- [ ] 死代码、未注册路由、stub、no-op 有明确状态；
- [ ] 代码修复后不再把旧缺陷写成当前状态；
- [ ] 历史存档与当前代码的冲突已标为历史。

## 2. 可理解性

- [ ] 标题下有一句电梯陈述；
- [ ] 先讲为什么，再讲类和函数；
- [ ] 说明输入、输出、调用方和失败行为；
- [ ] 至少有一条完整数据流；
- [ ] 代码片段后有逐块解释，而非重复注释；
- [ ] 解释了关键取舍（性能、隔离、准确性、兼容性）；
- [ ] 新术语链接到 Glossary；
- [ ] 新成员可以据文档找到下一份应读文件；
- [ ] 有“常见问题/注意事项”，但不把猜测写成事实；
- [ ] 长表格前有散文导览，读者知道表格回答什么问题。

## 3. 技术深度

- [ ] 核心数据结构逐字段或逐组解释；
- [ ] 公开方法表包含签名要点、调用方、失败行为；
- [ ] 至少两段真实代码走读；
- [ ] 代码块带 file:line 或稳定文件锚点；
- [ ] 涉及并发时说明锁、线程、协程、取消和超时；
- [ ] 涉及数据库时说明表、关键列、索引和写入时机；
- [ ] 涉及 API 时说明请求、响应、状态码和前端调用方；
- [ ] 涉及配置时说明变量、默认、消费者、未接线状态；
- [ ] 涉及外部依赖时说明降级与恢复动作；
- [ ] 至少一个可执行命令或 SQL 示例经过核对。

## 4. 关联信息

| 改动类型 | 应同步检查 |
|---|---|
| 新表/列 | schema、DatabaseSchema、模块产出表、Python reader |
| 新 C++ 路由 | CROW 注册、Swagger、EndpointsFlat、API 参考、前端 service |
| 新 Python 路由 | `_register_routes`、Pydantic 模型、Python API、vite proxy、前端 service |
| 新任务字段 | route handler、AnalysisTask、serialization、tasks.json、前端 modal |
| 新平台工件 | parser、core 编排、DB operations、SQL、LLM mapping、平台路由 |
| 新前端页面 | routes、Layout 导航、service、store/hook、测试、i18n |
| 新配置项 | C++/Python 读取点、.env.example、Environment、Installation、运维手册 |
| 缺陷修复 | 代码测试、模块注意事项、FAQ、Troubleshooting 已知问题表 |

## 5. 代码评审问题

- [ ] 这段实现是否真的被入口调用？
- [ ] 是否存在同名的另一条旧链路？
- [ ] 删除/取消后迟到 worker 会不会写回？
- [ ] 路径是否经过 task_store/FTS/提取围栏？
- [ ] 失败会返回错误还是静默空成功？
- [ ] 202 是否有精确 job id 轮询？
- [ ] 状态是否大小写一致？
- [ ] SQLite 写入列数与 placeholder 是否一致？
- [ ] PG JSONB 是否整体重赋值？
- [ ] 外部连接/线程/临时文件是否确定关闭？
- [ ] 代码中的注释是否与实现一致（TaskWatchdog 60s 注释 vs 1s 实现是反例）？
- [ ] 测试是否被真实 runner 收录？

## 6. 文档评审问题

- [ ] 是否把代码清单误当成解释？
- [ ] 是否有一段“读完后你应该理解什么”？
- [ ] 是否把历史计划写成已实现功能？
- [ ] 是否把单测可达写成生产可达？
- [ ] 是否注明示例中的路径/端口是占位还是默认？
- [ ] SQL 是否能直接在真实库执行？
- [ ] 示例响应是否避免编造精确数据？
- [ ] 相对链接是否存在？
- [ ] 文末日期是否准确？
- [ ] 新文档是否已加入对应索引？

## 8. 评审结论模板

```text
事实源：源码 commit / 迁移版本 / 运行环境
文档范围：文件、章节、模块
已核对：端点、字段、表、命令、代码锚点
发现问题：按严重程度列出
未能验证：外部服务/权限/平台依赖
测试：命令与结果
后续同步：需要修改的索引/FAQ/运维文档
```

## 9. 严重度判定

- **P0**：错误会破坏证据完整性、跨任务隔离、认证边界或造成数据静默丢失；必须阻断发布。
- **P1**：核心用户流程不可用、状态机不一致、跨服务契约漂移或生产数据静默为空；应在当前迭代修复。
- **P2**：功能可用但结果不完整、性能退化、错误信息不准确或文档误导；排入近期修复。
- **P3**：可维护性、示例、术语、格式或非生产死代码问题；可随文档/重构处理。

评审结论不能只写“测试通过”：应同时写清未覆盖的外部服务、未接线代码和已知降级边界。

---


### 9.1 证据优先原则

P0/P1 的判定必须能指向源码、日志、数据库或测试结果；不能仅凭 UI 空状态下结论。路径类问题优先检查任务归属，状态类问题优先检查大小写和终态集合，数据库类问题优先检查真实 DDL 与生产调用方。修复后重新执行最小复现，并把结果写进 commit 与对应文档。


### 9.2 评审记录字段

- 事实源与 commit
- 受影响用户流程
- 数据完整性判断
- 认证与路径边界
- 测试命令和结果
- 外部依赖状态
- 未覆盖范围
- 后续修复责任人
