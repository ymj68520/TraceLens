# 容量规划

> 回答："我有一块 X GB 的镜像、N 个并发任务，需要多少磁盘/内存/时间？" 所有数字要么来自仓库内实测/代码常量（标注来源），要么是明确标注的估算。规划原则：**先测同类小样本，再按比例外推**——本页给外推的系数和公式。

## 1. 实测基线（可直接引用的两个数据点）

| 指标 | 900MiB 真实 Ubuntu（GPT+FAT32/ext4，稀疏） | 100MB 裸 ext4（tests/test_image.img） | 来源 |
|------|------|------|------|
| raw.db files 行数 | 3,557 | ~数百 | 2026-08-23 全链实测（docs/testing/TestFixtures.md 的生成脚本产出） |
| files.db 分类行数 | 1,918 | ~两百 | 同上 |
| LLM 描述条数 | 78（云端端点） | 0（smart 淘汰/未开） | 同上 |
| Linux 工件表 | 正常产出 | — | 同上 |
| 雕刻 | 与源字节一致（byte-identical 验证） | — | 同上 |

**外推系数（估算）**：常规系统镜像的 files 行密度约 **3~8 行/GiB**（取决于文件数密度；开发机镜像密度高、数据盘低）。1TB 服务器镜像 ≈ 3k~8k 行 raw——**行数不是瓶颈，文件个数才是**（遍历与 per-file 处理成本）。

## 2. 磁盘容量模型

任务目录五类产物的大小排序（经验）：

| 产物 | 大小模型 | 备注 |
|------|---------|------|
| `extracted_files/` | ≈ 被提取文件总字节 | 最大户；过滤画像/LLM 限额直接控制 |
| `carved_files/` | ≈ 命中签名的未分配空间字节 | 开雕刻才有；30% 余量建议 |
| 各 .db | 行数 × 行宽（raw 每行 ~200B 估算；linux.db 73 表全开约行数×几百 B） | 1TB 镜像全部库合计 GB 级（估算） |
| 搜索索引 | 建索引目录 | 与被索引文本量同数量级 |
| 审计库 | 每动作一行，持续增长 | 无自动轮转（Monitoring 建议阈值 2GB 归档） |

**规划公式（估算）**：`任务盘 ≈ Σ(镜像大小 × 提取率 + 雕刻量) × 并发保留任务数`。保守取镜像总量的 0.3~0.5 倍/任务（提取+雕刻全开时），只分析不提取则 GB 级/任务。

## 3. 计算与内存

| 资源 | 模型 | 出处 |
|------|------|------|
| 分析并发 | `THREAD_POOL_SIZE`（默认 4）个任务同时跑 | TaskManager.cpp:31 |
| 每任务内存 | TSK 句柄 + SQLite cache + 提取缓冲；常规镜像数百 MB 级（估算） | — |
| LLM 实际并发 | 1（LLMClient 全局互斥——即使池开了 N 线程） | Concurrency §2.5 |
| Python 侧 | 单事件循环 + 少量 to_thread；markitdown 批量 Semaphore(4) | Concurrency §3 |

**推论**：分析吞吐随 THREAD_POOL_SIZE 增长直到磁盘饱和；LLM 吞吐不随它增长（串行闸在客户端互斥）。内存规划 = 基线 + N×每任务内存，N=THREAD_POOL_SIZE。

## 4. 时间预算

- **阶段权重 ≠ 耗时**：进度条按权重（IMAGE_ANALYSIS 25% 等），但真实耗时分布取决于镜像——文件数多的镜像 IMAGE_ANALYSIS 与 FILE_CLASSIFICATION 占大头；LLM 占比取决于文件量与限额。
- **看门狗的容量含义**：单任务任一阶段**超过 30 分钟无进度百分比变化**会被判死（TASK_WATCHDOG_STALE_MINUTES）。超大镜像要么确保阶段内汇报（大阶段内部有进度回调），要么调大该 env。
- **LLM 时间（估算）**：每文件 ≈ 内容 6144 字符（FileAnalyzer 预算上限推导）≈ 1.5~2k token 输入。千文件 smart 模式 ≈ 数十分钟量级（本地 20B 级模型）；GRAPHITI 摄取另计（每 episode 一次抽取+嵌入）。
- **建索引**：与被索引文本量线性；全量提取目录的建议先 filter 后 index（FullTextSearch 教程）。

## 5. 并发容量决策表

| THREAD_POOL_SIZE | 适合 | 注意 |
|------------------|------|------|
| 2 | 单盘机械盘/内存 ≤8G | LLM 串行下 2 已够喂本地端点 |
| 4（默认） | 均衡 | LLM 并发仍是 1；分析并发 4 |
| 8 | NVMe+大内存批量 backlog | 磁盘随机 IO 与 LLM 队列都需观察；THREAD_POOL_SIZE 同时放开两道闸（FAQ Q50） |

## 6. 容量问题的三个早期信号

1. 任务长时间 PENDING（池满）→ 降单任务成本（过滤画像/限额）优于盲目加线程；
2. files.llm_analyzed_at 覆盖率低 → LLM_MAX_FILES/smart 截断（不算故障，是限额）；
3. 磁盘水位 >80%（Monitoring 阈值）→ 先清 extracted/carved（DataAndBackup 的删除顺序）。
